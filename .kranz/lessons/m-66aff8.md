One durable, repo-specific planning lesson surfaced and was validated twice this mission — the a3 false-positive gate. It complements the existing anti-vacuity lessons with a new failure mode they don't cover, and it directly changes how a future planner picks contract test-filter substrings.

When a `command` assertion filters tests by a substring (e.g. `cargo test -p kranz-engine --test merge_test refus`), the count guard `test result: ok\. [1-9][0-9]* passed` does NOT protect against a substring that collides with a PRE-EXISTING passing test: here `refus` matched the existing `dirty_tracked_tree_is_refused_without_running_gates_or_touching_base` (asserting `RefusedDirtyTree`), so a3 reported "1 passed" and gated GREEN with zero implementation of the required `RefusedPreMerge`. Before shipping a contract, grep the repo's existing test names for every filter substring you choose; pick a substring that matches ONLY the not-yet-written test (or pin `--exact` / a unique prefix), because a nonzero-but-wrong-test match is just as vacuous as a zero-test match and the count guard cannot catch it.
