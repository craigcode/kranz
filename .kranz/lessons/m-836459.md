A durable, repo-specific pattern showed up clearly this mission: both ms-2 validation rounds raised findings for error/degradation branches that were implemented and code-verified but not exercised by a test — costing a fix cycle. That's a reliable trait of this repo's milestone validators worth pre-empting in how future feature specs are written.

When a feature's validationCriteria names an error or degradation branch (returns Err, 404, a 5xx-not-panic, or degrades-to-null), state explicitly in that feature's spec that the worker must add a test exercising that exact branch — not just implement it. This repo's milestone validators reliably raise a finding (and force a fix cycle) for any such branch that is implemented but only code-verified rather than test-covered, even when the happy path and adjacent cases are tested. Bake the error-branch test into the criteria up front so the first worker covers it.
