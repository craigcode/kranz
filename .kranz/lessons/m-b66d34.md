When adding a headless-CLI backend (the backend_codex/droid/kimi pattern), remember the mock/stub tests NEVER spawn the real CLI — so CLI-boundary correctness is invisible to the entire green gate (a1–a4 all pass while the backend is actually broken). `effective_model` passes the configured/default model straight to the CLI's `-m` flag with no translation, so `DEFAULT_<BACKEND>_MODEL` must be the exact id form the CLI accepts (kimi needed `kimi-code/k3`, not bare `k3`, which fails `config.invalid` at real invocation); effort may be a separate env var/flag rather than a model suffix (kimi: `KIMI_MODEL_THINKING_EFFORT`, not a `-m` suffix); and token usage may be off the output wire entirely (kimi's is, so runs silently record $0 cost). Verify these against the committed probe fixture/doc, not the test suite, and pin the default model id to the CLI-accepted form in the plan — the orchestrator must catch this in review because no test will.
