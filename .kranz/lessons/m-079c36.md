A vacuous-test-pass trap dominated this mission's cost (multiple validation rounds, two waiver cycles, and a real final-gate integrity risk), and it's durable and repo-specific — worth carrying forward:

When a validation-contract assertion is `cargo test <exact-test-name> 2>&1 | grep -qE 'test result: ok\.'`, it passes VACUOUSLY if `<test-name>` matches zero tests — cargo prints `test result: ok. 0 passed; N filtered out` when the test doesn't exist yet, and the grep matches. This silently green-lights every not-yet-written assertion at each milestone gate AND at the final gate. Two consequences for future planners in this repo: (1) make the command require a nonzero pass count, e.g. `grep -qE 'test result: ok\. [1-9][0-9]* passed'`, and pin `--test <file>` so only one test binary's summary line is matched; (2) don't author a mission-wide contract whose assertions are implemented by later milestones — early milestone gates will run those commands against absent tests and pass vacuously, forcing waiver cycles. Either scope each assertion's test to its milestone or accept that early gates need explicit waivers.
