The mission's real cost this time wasn't the code — both features landed cleanly on the first run — it was three validation rounds and two waivers burned on a contract-command defect that a future planner in this repo will re-hit unless warned. That's a durable, repo-specific, planning-shaping lesson.

LESSON: When writing a validation-contract "passed-count guard" over a long-running, high-volume test writer in this repo (`cargo test --workspace` emits ~38 crate/binary summaries over ~1000+ lines; `vitest run` similarly), NEVER use `grep -q` together with `set -o pipefail`. `grep -q` exits on its first match and closes the pipe; the still-writing process (cargo/vitest) then dies on SIGPIPE with exit 101, and `pipefail` propagates that 101 as the pipeline's status — failing the assertion even though every test passed. It bit only the full-workspace/full-suite commands (a3, and intermittently a2), while the narrow single-binary command (a1, `cargo test -p kranz-server <one test>`) passed because its output is small enough to finish before grep exits — so it slips through feature-level checks and only surfaces at milestone validation, costing fix cycles and waivers. Write the guard as `grep -cE 'test result: ok\. [1-9][0-9]* passed'` (check the count), or drop `-q` (only the exit status is used), or interpose `tee`/`cat` to keep the reader open until the writer finishes. Also note a2/a4 (anything in apps/dashboard via `npx vitest`/`tsc`) require the dashboard's node_modules to be installed (`npm ci`) in the validation environment.
