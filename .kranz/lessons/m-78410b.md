A genuinely reusable, repo-specific trap surfaced here — and this repo's acceptance hints actively steer future planners toward the exact pattern that triggers it, so it's worth carrying forward.

For any `cargo test --workspace` contract assertion, do NOT wrap `... 2>&1 | grep -qE 'result: ok\. [1-9][0-9]* passed'` in `bash -o pipefail`: `grep -q` closes the pipe on its first match while cargo still has ~36 more test binaries to stream, cargo panics on the broken-pipe write (exit 101), and pipefail propagates that as a failure even when every test passes — a deterministic false-negative at the final gate. Write the assertion pipe-tolerant: either the brief's original form without pipefail (only grep's exit status counts, so it returns 0), or capture first — `out=$(cargo test --workspace 2>&1); printf '%s' "$out" | grep -qE 'result: ok\. [1-9][0-9]* passed'`. Also note the orchestrator cannot revise a contract command mid-mission, so a defective assertion string can only be waived, never fix-featured — get the command right at plan time.
