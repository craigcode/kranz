The one real cost this mission was a full f-2-3 respawn traceable to f-2-2 never running `cargo fmt` — and the trap was made worse because the *next* fresh worker detected the diff but misattributed it as "pre-existing" (it had no mission-wide context to know those lines were mission code). That's durable, repo-specific, and directly shapes how a future planner writes feature criteria.

Spec every feature that edits Rust source with its OWN `cargo fmt --all -- --check` and `cargo clippy --workspace --all-targets -- -D warnings` validationCriterion — do NOT rely solely on a milestone-level fmt/clippy gate (the d11/d12 pattern). When several features edit one large shared file (e.g. crates/engine/src/orchestrator.rs), an unformatted addition from feature N stays green in N's own narrower test runs and only trips the workspace fmt gate later; the fresh worker on feature N+1 then sees the diff but, lacking mission context, reports it as "pre-existing/pre-mission out-of-scope" and leaves it — so it survives to milestone validation and costs a respawn to fix. Per-feature fmt/clippy criteria force the violation to be caught and owned in the feature that introduced it.
